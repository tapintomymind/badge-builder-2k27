5. DEVIATIONS FROM THE BRIEF — four, all measured, none improvised
================================================================================

D1. `.rail-column` — ONE structural element beyond the brief's JSX. NECESSARY.
    A sticky GRID ITEM is constrained by the grid CONTAINER's content box, not
    by its own grid row. Chrome confirms this: with the two .panel-below divs
    now occupying rows 2 and 3, a sticky .rail-left placed directly in .layout
    scrolled clean out of the badge grid and painted on top of the Synergy
    panel.  MEASURED at 1280, scrollY 4648:
        rail doc-top 4660 / doc-bottom 5536
        grid ends at 4644, #panel-synergy starts at 4668   -> OVERLAP
    Four no-new-element candidates were tested empirically and ALL FOUR failed
    to change the clamp by a single pixel: `grid-row: 1 / 2`, `align-self:
    stretch` on .rail-left, `height: fit-content`, and explicit row templates.
    Wrapping .rail-left in a stretching grid item clamps it correctly:
        rail doc-top 3768 = 118 + 4526 − 876 = exactly the bottom of row 1
        overlap: false
    .rail-column carries NO landmark, NO id, NO storageKey, NO state and one
    CSS declaration (`align-self: stretch`, L only). .rail-left keeps every
    rule the brief specifies, so T7's overflow guard still inspects the real
    overflow surface and the frozen `.rail-left .segmented__track` selector
    still matches — verified live: 3 × 87.33px, matching §13.0.1's predicted
    "3 × ~88px" at a 266px content box. Pinned by a new source assertion.

D2. `.ledger-overview__label { min-width: 0 }` -> `min-width: max-content`.
    §13.4's CSS as written COLLAPSES the label column to zero. `1fr auto`
    sizes the auto track from its content first; the over-budget row's metrics
    max-content is 303px against 230px of available track, so auto takes the
    entire box and the fr track — whose automatic minimum `min-width: 0`
    explicitly removes — resolves to 0. MEASURED with the spec's literal CSS:
        grid-template-columns: 0px 230px    (all six labels 0px wide)
    Every label then overflowed a zero-width column and abutted its own
    numbers. It renders almost-plausibly, which is why no test caught it.
    With `min-width: max-content`:
        grid-template-columns: 77.41px 152.59px
    §13.4's stated intent — "the label stays on line 1", metrics wrapping
    inside their own column — is now what actually happens. The `min-width: 0`
    on .ledger-overview__metrics is unchanged and still correct; it is only
    the LABEL that must not be allowed to collapse.

D3. `.synergy-panel` floor takes §11.5 ③'s min() sub-floor idiom:
        repeat(auto-fill, minmax(min(426px, 1fr)…))  ->  minmax(min(426px, 100%), 1fr)
    A bare 426px grid floor is ABSOLUTE. At 390 the single track stayed 426px
    inside a 366px box and the whole DOCUMENT grew a horizontal scrollbar —
    MEASURED: scrollWidth 455 vs clientWidth 390. §13.5's own table says the
    390 row is "366, stacked", which is only true with the min() clamp; the
    spec asserted the shrink-to-fit behaviour and then wrote CSS that forbids
    it. Fixed with the repo's existing, already-tested idiom. 426 is still ONE
    derived number used TWICE (track floor + container threshold), and the
    floor still binds at every width that can fund it. After: no horizontal
    scrollbar at any of 390 / 768 / 1280 / 1440 / 1339 / 1340 / 1356 / 1357.
    CONSEQUENCE, handled: ATTR_CELL_FLOOR parsed the FIRST min() idiom in the
    file, and .synergy-panel is declared ABOVE the attribute grid — so it
    would have silently returned 426 and every I9 assertion would have been
    grading the wrong surface while staying green. ATTR_CELL_FLOOR is now read
    out of cssBlock(app, ".attr-group__fields--sliders"). Same class of trap
    as T5's, same fix as T9's: anchor the parse to the surface that owns it.

D4. The @container block was MOVED below `.synergy-row__pickers`'s base rule.
    §13.5 lists it immediately after `.synergy-row { container-type }`, but in
    the shipped stylesheet `.synergy-row__pickers { flex-direction: column }`
    is declared ~40 lines LOWER. A container query carries no specificity of
    its own, so at the spec's position the query evaluated TRUE at 1280 and
    changed nothing — pickers stacked in a 601px row while every assertion in
    the suite stayed green. MEASURED before the move: containerType
    "inline-size", row 601px, pickersFlexDir "column". After: "row".
    Pinned by a new ordering assertion so it cannot regress.

T16 — THE CONTAINER-QUERY BAND IS NOT EMPTY, and a tested width lands in it.
  T16 predicted the query fires at border-box >= 460 rather than 426 (426 is a
  border-box figure but a size query evaluates against the CONTENT box, and
  .synergy-row is a fieldset with 1px borders and --space-4 sides: 2 + 32 =
  34px of chrome). T16 then ruled it conservative-safe "because no tested
  width lands in the 426–460 band". MEASURED: 1440 DOES.
      1280 -> row 601 -> content 567 >= 426  -> pickers SIDE BY SIDE
      1440 -> row 450 -> content 416 <  426  -> pickers STACKED
       768 -> row 702 -> content 668         -> side by side
       390 -> row 332 -> content 298         -> stacked (intended)
  So at 1440 the pickers stack while at 1280 they do not — which contradicts
  §4.3's "1440: everything else identical to 1280". Failure direction is still
  conservative (stack, never crush) and §6's stop condition #12 is scoped to
  1280, which is green — so per T16's explicit instruction I did NOT re-derive
  the number. Designer's call. The one-line fix is a threshold of 460, or
  moving container-type onto a box whose content edge is the row's border edge.

  ROOT CAUSE OF THE 1440 CASE — §13.0.1's below-grid table omits Section
  chrome. It derives row widths straight from `belowGrid`, but both panels sit
  inside a <Section> that costs 34px. Re-derived against the shipped tree:
      1280: 1248 − 34 = 1214 ; (1214 − 12)/2 = 601   (§13.0.1 says 609)
      1440: 1408 − 34 = 1374 ; (1374 − 24)/3 = 450   (§13.0.1 says 455)
  The 5px at 1440 is exactly what drops the content box from 421 to 416 and
  under the threshold. Worth folding into rev 7's arithmetic generally: it is
  the same class of omission as I12's (a decoration the geometry did not know
  about), one level up.

C5 — the 76 ÷ 9 chars monospace bridge is unsound, and here is why it looked
  right. §13.0.1 derives 8.44 px/char from "Rebounding" = 76. But "Rebounding"
  is TEN characters, and it renders in the PROPORTIONAL --text-sm UI face, not
  in --font-num. Measured, "Rebounding" is 77.41px.
  What 76 actually is, is the EMPTY-STATE METRICS string: "0/0 · 0/—" is nine
  --font-num characters and measures 75.86px — 9 × 8.43. The two constants
  coincidentally shared a value, and the derivation note attached itself to
  the wrong one. The advance itself is sound (8.429 px/char, confirmed twice
  independently above); only the bridge is wrong. Recommend rev 7 restate it
  from the metrics string and re-pin LEDGER_LABEL_MAX at 78 (measured 77.41),
  which the slack still funds (25.59 against SPACE_6 24).

The over-budget row wraps with the middot leading the second line
("· 11/9 over by 2 ⚠"). Inherent to wrapping a composite string; P0-1's
