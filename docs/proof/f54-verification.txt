1. BLOCKING IN-SLICE GATE — NUMERIC_H RE-MEASURED IN HEADLESS CHROME
--------------------------------------------------------------------------------
Chrome/151.0.7922.174, --headless=new, driven over CDP
(Runtime.evaluate on the live dev server), .number-field input inside
.attr-slider__num, viewport 1280.

  deviceScaleFactor 1  ->  offsetHeight  26   getBoundingClientRect 26.000
  deviceScaleFactor 2  ->  offsetHeight  27   getBoundingClientRect 26.500

PINNED VALUE UNCHANGED AT 27, and the choice is deliberate. 27 is the larger
of the two, per §13.0.1's take-the-larger rule (the same rule that governs
SYNERGY_HEADER_MAX and that re-pinned LEDGER_LABEL_MAX 76 -> 78 in this
slice). A larger SLIDER_H yields a LOWER derived slider count, so the I15
floor is the PESSIMISTIC bound; deriving from the dpr-1 value would make the
floor optimistic on a Retina display, which is the wrong direction for a
floor. Both measurements sit inside the brief's 26-28 band, so the stop
condition did not fire and the floor did not relax.

Consequences, recorded rather than assumed:
  derived  SLIDER_H = 81      measured (dpr 1) 80.0
  derived  ATTR_STACK_H = 2016 measured (dpr 1) 1996, (dpr 2) 2006
The model over-estimates by 0.5px per slider = 10px over the stack. It is
conservative in the same direction as the pin, and the measured visible-slider
counts match the derived floor exactly (below).

12. AMENDMENT LANDED MID-SLICE (Designer §17, via the coordinator)
--------------------------------------------------------------------------------
The scoped `hasValues` expresses its budget half as a DERIVED predicate over
the Budget record rather than an enumerated `points || equipSlots`:

  const hasBudgetValues = CATEGORIES.some((category) =>
    Object.values(budgets[category]).some((value) => value > 0));

Equivalent to the shipped sum test because every budget field is clamped at
min 0 (BudgetGrid), so a positive sum and a positive member are one question.

REACHABILITY, checked against the queued work rather than assumed. Any new
member of `Budget` is picked up for free. But `a5-e-bonus-engine` models the
bonus layer as a SEPARATE `BonusBudget` on WorkingState -- earnedEquipSlots,
earnedPoints, appliedEquipSlots[6], appliedPoints[6] -- and A5-R1/A5-R4
deliberately never merge it into `budgets`; `Budget` itself is unchanged on
that branch. So the derived form does not by itself reach the bonus fields:
they are not in the record BuildPanel receives. When the bonus UI slice lands
it must pass the bonus totals into BuildPanel and add them to this predicate,
or a user whose only input is bonus gets a setup panel that never latches.
Flagged here so it is a hand-off and not a silent gap.
