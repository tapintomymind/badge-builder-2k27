3. THE ADDITIVE GUARANTEE, MEASURED RATHER THAN PROMISED
--------------------------------------------------------------------------------
Method: build origin/dev @4d1ba88 and this branch, serve both from `vite preview`
(ports 5184 and 5183), seed the IDENTICAL autosave into each after clearing
localStorage, and take a census of every element inside each shipped region --
tag, class, and box measured RELATIVE TO THAT REGION'S OWN top-left. Compared as
a multiset, so one inserted node cannot report every node after it as "moved".
Zero-box elements (a <thead> under a CSS grid, an <option>, display:contents)
report a rect at the document origin, so their region-relative offset moves by
exactly the region's displacement; they are counted, never positioned.

5. THE #badge-* LANDING, IN BOTH SCROLL MODES
--------------------------------------------------------------------------------
The board's tiles are the first anchors in the app that point INTO a category
section, so the landing position is new and is derived rather than typed:

  .grid-section__cards > li {
    scroll-margin-top: calc(var(--sticky-stack-h) - var(--scroll-reserve));
  }

A card sits under BOTH sticky layers (nav 44 + digest 76 = 120), unlike
`.grid-section`, which lands under layer 1 alone. scroll-padding-top and
scroll-margin-top ADD, so the reserve is subtracted and cancels. Measured by
clicking a real tile and reading the rects:

  mode                        scroll-padding  scroll-margin  card top  digest bottom
  document scroller (700h)         0px           120px         120         120
  app shell, .col-right (768h)   120px             0px         290         290

ONE landing position in both modes: the card's top edge is flush with the
bottom of the sticky stack, clearing it by 1px. A naive `scroll-margin-top:
120px` would land at 240 under the shell -- the whole reserve of overshoot,
invisible on the document scroller and wrong in the mode the app runs in.

7. WHAT THE BOARD REFUSES TO RENDER
--------------------------------------------------------------------------------
There is no "Your Build Has No <Discipline> Badge Slots" state, because the app
has no channel that can tell a genuine zero from a field the user never filled
in. 2K's own screen carries that sentence; ours cannot honestly say it. Both
cases render identically -- the shipped `Badge Slots capacity not set` hint, an
em dash for the capacity, no fence, no empty cells, no over-by -- which is the
ruling in force. Asserted in tests/ui/f16-loadout-board.test.tsx group 4.

No 2K27 number is modelled anywhere on this surface. Every figure on the board
is one the engine already computes for another shipped surface, and the two
over-by strings are imported from the one builder rather than authored here.
