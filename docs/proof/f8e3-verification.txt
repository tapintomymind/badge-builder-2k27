4. INV-20 — CAPACITY-FREE INERTNESS, PROVED TWO WAYS
=============================================================================
THE THEOREM. No move ever decreases the entry count (adds raise it, upgrades and
exchanges hold it), and exchanges are offered only at equipSlotsUsed >=
equipSlots. So a walk that ENDS below capacity was below capacity at EVERY
iteration, was never offered an exchange, and is the two-move walk verbatim.

  (a) property : 735 capacity-free rolls, 0 exchange steps.        735/735
  (b) differential: every capacity-free roll is BYTE-IDENTICAL to a
      reference two-move walk driven by the same seed.             735/735
  (c) golden : six capacity-free fixtures pinned byte-for-byte.    6/6

ON (b) RATHER THAN GOLDENS COPIED FROM THE E2 RUN — a deliberate deviation from
the brief, and the reason is the brief's own mechanism. ROLL_ALGORITHM_VERSION
rides inside the per-category RNG seed string (`${seed} ${VERSION} ${category}`)
precisely so that a version bump changes the stream. At version 2 the same seed
therefore CANNOT reproduce version-1 output — that is the mechanism working, not
a regression, and it is why literal E2 goldens are unconstructible here. What the
theorem actually claims is that the two-move and three-move walks AGREE wherever
no exchange is offered; (b) compares them at the same version, which is that
claim tested directly and is strictly stronger than a frozen output blob. The
checked-in golden in (c) is from THIS implementation and is labelled as such.

8. THE TWO CONTRACT CORRECTIONS
=============================================================================
A4-R1 — `fill` ADDS, `reroll` REBUILDS.
  `resolvePins` gains a fourth implicit-pin arm: in `fill`, every existing entry
  not otherwise pinned is held `exact` with the new PinReason `"fillDefault"`.
  `pins` is now a POSITIVE PERMISSION GRANT in both modes, so a forgotten pin
  fails CLOSED in the mode where failing open is invisible. The note is emitted
  only for entries that actually had a suppressed affordable upgrade, computed
  by re-running the enumerator at the end of the walk with the fill-held entries
  treated as unpinned — the same shape newBadgesBlockedByBadgeSlots already uses.
  The caller-obligation paragraph is DELETED from the `pins` field doc and
  replaced with the structural rule.
    INV-5b   500 seeds x 20 states: every entry absent from `pins` is
             byte-identical after a `fill`
    INV-5b   an explicit `include` still re-opens the entry (the grant works)
    INV-5b   the note fires only where the rule cost something
  Also de-vacuumed: the AJ-11 `fill` decline test's
  `steps.every(s => !s.requiresNewBadgeSlot)` is now vacuously true under A4-R1,
  so the assertion is made explicit (`steps` is []) and a second arm added with
  `include` pins where fifteen upgrades genuinely fire.

A4-R2 — the termination bound.
  `rollIterationBound(entriesAtStart, equipSlots, ceilingSpend)`:
    4 * (max(entriesAtStart, equipSlots) + ceilingSpend) + 1
  with ceilingSpend = min(points, legalCeiling) computed by the new
  `ceilingSpendFor` in steps.ts. The third argument is REQUIRED, not defaulted —
  a silently-omitted argument would produce a bound that is too tight in exactly
  the capacity-bound case the exchange move exists for, and a FALSE THROW is the
  one failure a backstop must not have. The existing two-argument unit test was
  updated (the ceilingSpend-0 case still yields 13 / 13 / 21, so the ratified
  two-move form survives as a special case rather than being replaced).

    INV-17  AJ-11 REGRESSION FIXTURE: 5 entries against capacity 1, `fill`, both

9. THE ENLARGED SWEEP, AND ONE FINDING IT PRODUCED
=============================================================================
E2's 200 fixtures were all makeBuild(78, attrs) — twenty equal attributes at one
height. The second family adds 240 fixtures with per-attribute spreads across
seven heights, deterministically generated in tests/randomize-oracle.ts.

FINDING, disclosed rather than repaired. On the first run of the enlarged sweep
the capacity-free max was 4 and one roll breached the hard cap. Root cause was
NOT the engine: INV-23's `synthetic-exchange-plus-four` is legal ONLY at HOF — a
shape no shipped badge has — and it had been added to the `syntheticBadges`
barrel, which tests/randomize.test.ts splatted into the sweep dataset. In a
capacity-free Physicals pool of 12 that fixture turns the category into an
exact-cover problem greedy can miss by 4.

  with the pair in the dataset:    free max 4, 1 roll over the cap
  without it:                      free max 2, 0 rolls over the cap
  and the offending roll is CAPACITY-FREE, hence byte-identical to the two-move
  walk at the same seed — F8-E2's engine produces exactly the same result, so
  the exchange move neither caused it nor could fix it.

Fix: the sweep dataset is pinned to a NAMED SET (the E1/E2 fixtures), which is
the same reasoning tests/feasibility-golden.test.ts already records for its own
dataset, and which additionally makes the `equal-attributes` family a true
reproduction of what E2 measured. INV-23 and INV-22 reach their pair through
isolated datasets. The finding itself is pinned as a test —
"the adversarial fixture, disclosed" — so it is on the record and so nobody
re-splats the barrel into the sweep without seeing it.

ONE DEVIATION FROM THE BRIEF, recorded rather than smoothed:
  The brief's walk pseudocode ends every iteration with `rollCreated.add(
  chosen.badgeId)` unconditionally. Implemented that way, an UPGRADE of a
  pre-existing entry would enrol that entry as exchangeable — and an `include`
  pin permits exactly such an upgrade on an entry the USER placed. The roll
  could then trade the user's own badge away, which is the precise failure
  INV-5 exists to prevent. The implementation enrols on ADDS and on the incoming
  side of an EXCHANGE only; upgrades enrol nothing. INV-21 pins it.
