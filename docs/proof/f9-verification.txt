HOW EVERYTHING BELOW WAS MEASURED
--------------------------------------------------------------------------------
Chrome/151.0.7922.174 --headless=new driven over CDP, deviceScaleFactor 1 (2 for the
PNGs), against a PRODUCTION BUILD of each tree served by `python3 -m
http.server` on two throwaway ports:

  BEFORE  dev @a5fe8e1        http://127.0.0.1:5391
  AFTER   f9-touch-floors     http://127.0.0.1:5392

NO DEV SERVER WAS STARTED. vite.config.ts pins 5173 with strictPort, every
worktree in this repo shares that origin, and localStorage is keyed to origin
INCLUDING port — a stale-code mount on 5173 can strip fields out of the
operator's real saved builds. Both measurement origins are distinct ports, so
neither tree could see or write the operator's data.

Every state below was reached by a REAL event, never by poking React state:
  · the quarantine banner, by seeding an autosave the deserializer must refuse
    (Page.addScriptToEvaluateOnNewDocument, so it runs before the app boots)
  · the saved build, by typing into the BuildManager footer and clicking
    `Save as new`
  · the reset dialog, by committing a slider and clicking `Reset build`
  · the import dialog, by capturing the app's OWN export Blob through a
    patched URL.createObjectURL and handing the bytes straight back to the
    file input as a File

4. THE JUMP NAV — THE SEVENTH SURFACE, AND THE ONE WITH A BUDGET
--------------------------------------------------------------------------------
Not one of the six, found by the census, and the most-tapped row on a phone:
its chips were 28px. §5.3's sticky-budget table already specifies what layer 1
is made of — "44px chips (the touch floor — this layer cannot shrink) + 2px
padding each side" — so the chips take the floor and the nav's padding drops
from --space-2 to the 2px the budget actually funds.

  MEASURED AT scrollY 4200, 390 x 844, with a digest stuck:

                       BEFORE            AFTER
    jump nav           top 0, h 44       top 0, h 48   (cap: <= 48)
    stuck digest       top 44, h 59      top 48, h 59  (cap: <= 88)
    gap between        0.00              0.00
    two-layer total    103               107           (cap: <= 136)
    doc h-scrollbar    none              none

The digest's `top` is re-derived, not re-typed: `calc(var(--tap-target) + 4px)`
at S, which assertion 28 checks EQUALS 2 x the parsed S nav padding + the
parsed token. The base `top: 44px` is untouched and still equals the nav's
height at M and L, where the chips stay 28px — also re-derived (2 x --space-2
+ the parsed `.btn--sm` height = 44).

`.jump-nav`'s `overflow-x: auto` is inherited from the base rule and is NOT
added by this pass. §6 names it as the one permitted single-axis scroll, and
the chips' widths did not change, so the nav's scrollWidth is what it was.

6. THE §3.1 DIVERGENCE — DECLARED, NOT SILENTLY RE-PINNED
--------------------------------------------------------------------------------
§3.1 rev 2 ratified `sm` -> 36px and `md` -> 44px at S, and gave its reason in
one sentence:

    "The `md` variant is the one used for every header and dialog action, so
     raising it to 44 at S clears the rule for the whole set."

THAT PREMISE IS FALSE AGAINST THE SHIPPED TREE. Every header action, every
dialog action, every banner action, every BuildManager row action and both
Export/Import controls pass `size="sm"`. `grep -c 'size="md"' src/ui/**` is
ZERO; `md` is only the prop default, and no call site takes it. Shipping
§3.1's letter would have left the ENTIRE named set at 36px — still under §5.3's
own "every interactive target >= 44x44px", which is the invariant the §3.1
bullet exists to satisfy and which it cites in its own title.

RESOLUTION: the invariant wins. Both sizes clear 44 at S. §3.1's size bullet
needs a rev to match, and that is a decision for the spec's owner, not a
cleanup — recorded here and in the reportback rather than performed.

Assertion 25 pins the divergence from both ends: it asserts the base heights
are still 28 and 36 (so the S block stays load-bearing) AND that no file under
src/ui/ ships `size="md"` (so the premise stays false, or the test goes red and
someone re-reads this section).

ALSO OUT OF SCOPE, NAMED RATHER THAN OMITTED:
  · src/main.tsx's RecoveryBoundary renders three UNSTYLED native <button>s
    with inline styles, deliberately — that screen has to render when the
    stylesheet itself is the casualty. They carry no class, so no rule in this
    pass can reach them and none should.
  · `.segmented label:has(input:disabled) { opacity: 0.45 }` is an invariant I2
    violation (§6's disabled floor is 0.6, which F5.3 already applied to
    `.btn:disabled`). It is a contrast defect, not a target-size one, and
    changing it here would put a §6 edit inside a §5.3 slice. FLAGGED, not
    fixed.

TWO ITEMS REMAIN VISUALLY UNVERIFIED, for the same reason F5.3 recorded:
  · the keyboard :focus-visible ring on the newly-flexed controls
    (`.segmented label`, `.jump-nav a`, `.filter-bar__clear`, `.skip-link`).
    :focus-visible requires a TRUSTED interaction and CDP can only dispatch
    untrusted events, so programmatic focus correctly refuses to match. The
    rings are unchanged structurally — no rule in this pass touches
    `box-shadow`, `outline` or any :focus-visible selector, and `display`
    changes do not affect ring geometry on a box that only grew.
  · real-finger ergonomics. 44px is the standard's number, not a measurement
    of the operator's thumb.
